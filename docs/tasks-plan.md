## Задачи проекта

### Задача 1. Подключение к защищенной Kafka и конфигурация окружения
* **Тип:** Инфраструктура / Конфигурация
* **Описание:** Подключить стартер `spring-kafka` в проект, настроить защищенный протокол `SASL_SSL` с механизмом `SCRAM-SHA-512`. Вынести все параметры подключения (адрес брокера, логин, пароль, уникальный `group.id`, имя топика свечей) в переменные окружения и `application.properties`.
* **Ожидаемый результат:** Сервис успешно инициализирует Kafka-клиент при наличии подключения и не завершает аварийно работу при временной недоступности брокера.
* **Критерии готовности (Definition of Done):**
  - [ ] В `pom.xml` добавлена зависимость `spring-kafka`.
  - [ ] Переменные `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_USERNAME`, `KAFKA_PASSWORD`, `KAFKA_GROUP_ID`, `CANDLE_TOPIC` задокументированы в `.env.example`.
  - [ ] Секретные данные (логин, пароль, secretKey) отсутствуют в открытом виде в исходном коде и Git.
  - [ ] Сконфигурирован уникальный `group.id` для предотвращения конкурентного чтения свечей между студентами.

### Задача 2. Реализация базовых моделей сообщений и контрактов событий
* **Тип:** Разработка / Модели данных (DTO)
* **Описание:** Создать Java-классы/рекорды для событий платформы в соответствии с главой 5, 6, 7 и 8 документации: единую обертку сообщения (`EventEnvelope`), структуры для запроса регистрации, ответа регистрации и закрытой свечи.
* **Ожидаемый результат:** Строго типизированные Java-модели с поддержкой сериализации/десериализации в JSON (Jackson) и валидацией обязательных полей (`schemaVersion = 1.0`).
* **Критерии готовности (Definition of Done):**
  - [ ] Реализованы модели:
    - Общая структура: `eventId`, `eventType`, `schemaVersion`, `occurredAt`, `correlationId`, `causationId`, `producer`, `payload`.
    - `AccountRegistrationRequestPayload` (`secretKey`, `accountId`, `accountName`, `groupId`, `strategyId`, `strategyName`, `serviceName`).
    - `AccountRegistrationResultPayload` (`status`, `reason`, `accountId`, и др.).
    - `MarketCandleClosedPayload` (`runId`, `instrument`, `sequenceNumber`, `candleTime`, `open`, `high`, `low`, `close`, `volume`, `isWarmup`).
  - [ ] Модели корректно сериализуются без потери полей и типов.

### Задача 3. Автоматическая регистрация сервиса на платформе
* **Тип:** Разработка / Жизненный цикл
* **Описание:** Реализовать отправку запроса регистрации `account.registration.request` в топик Kafka сразу при старте сервиса, а также обработку входящего ответа `account.registration.result`.
* **Ожидаемый результат:** Сервис регистрируется на платформе, получает подтверждение `status = REGISTERED` и переходит в режим готовности к приему свечей. При получении `REJECTED` сервис логирует причину и блокирует отправку рекомендаций.
* **Критерии готовности (Definition of Done):**
  - [ ] Приложение отправляет запрос регистрации при событии готовности контекста (ApplicationReadyEvent).
  - [ ] Идентификаторы `accountId`, `strategyId`, `serviceName` стабильны между перезапусками.
  - [ ] Подписка на топик `account.registration.result` фильтрует сообщения по своему `serviceName` / `correlationId`.
  - [ ] При статусе `REJECTED` в журнал пишется понятное предупреждение, флаг авторизации сбрасывается в `false`.

---

### Задача 4. Подписка и потоковая обработка закрытых свечей
* **Тип:** Разработка / Прием данных
* **Описание:** Настроить Kafka-слушатель (`@KafkaListener`) на топик, указанный в переменной `CANDLE_TOPIC`. Организовать потоковое чтение событий `market.candle.closed` и структурированное логирование.
* **Ожидаемый результат:** Каждая входящая свеча принимается сервисом, ее цены, объем и `sequenceNumber` фиксируются в логах приложения.
* **Критерии готовности (Definition of Done):**
  - [ ] `@KafkaListener` настроен на чтение топика из свойства `${CANDLE_TOPIC}`.
  - [ ] Используется уникальный `group.id`, исключающий потерю свечей.
  - [ ] В логах отображаются: тикер, время свечи, цены (O/H/L/C), объем и порядковый номер `sequenceNumber`.
  - [ ] Сбои парсинга одного сообщения не останавливают поток чтения.

### Задача 5. Публикация базовой торговой рекомендации `HOLD` («холодный старт»)
* **Тип:** Разработка / Бизнес-логика
* **Описание:** Реализовать контракт ответа на полученную свечу: публикацию события `strategy.recommendation.created` в топик платформы со статусом `signal = HOLD`, `confidence = 0.0` и `suggestedQuantity = 0`.
* **Ожидаемый результат:** На каждую полученную свечу сервис своевременно отправляет одну рекомендацию `HOLD`, сохраняя `sourceEventId`, `runId`, `instrument` и `sequenceNumber`.
* **Критерии готовности (Definition of Done):**
  - [ ] Рекомендация публикуется в топик `strategy.recommendation.created`.
  - [ ] Поля `sourceEventId`, `runId`, `sequenceNumber` в точности скопированы из входной свечи.
  - [ ] Поле `secretKey` передается в теле рекомендации для авторизации.
  - [ ] Время публикации укладывается в окно ожидания прогона.

---

### Задача 6. Реализация торговой стратегии (RSI Reversal)
* **Тип:** Бизнес-логика / Алгоритмы
* **Описание:** Реализовать алгоритм расчета индекса относительной силы (RSI) с периодом 14 свечей. До накопления 14 свечей выдавать `HOLD`, при перепроданности (<30) — `BUY`, при перекупленности (>70) — `SELL`.
* **Ожидаемый результат:** Сервис формирует обоснованные торговые сигналы `BUY`/`SELL`/`HOLD` с динамическим расчетом уверенности (`confidence`) и рекомендуемого объема (`suggestedQuantity`).
* **Критерии готовности (Definition of Done):**
  - [ ] Корректный расчет приростов и убытков за период 14 свечей.
  - [ ] Генерация `BUY` при выходе из зоны перепроданности.
  - [ ] Генерация `SELL` при выходе из зоны перекупленности.
  - [ ] Изоляция состояния индикатора по парам `(runId, instrument)`.

---

### Задача 7. Отправка сигналов состояния (Heartbeat)
* **Тип:** Надежность / Телеметрия
* **Описание:** Настроить периодическую отправку события `account.service.heartbeat` каждые 5 секунд со счетчиками обработанных свечей и статусом сервиса (`UP`).
* **Ожидаемый результат:** Преподавательская платформа непрерывно видит сервис в статусе «в сети».
* **Критерии готовности (Definition of Done):**
  - [ ] Шедулер `@Scheduled(fixedRate = 5000)` отправляет heartbeat раз в 5 секунд.
  - [ ] `instanceId` уникален для каждого старта процесса.
  - [ ] Счетчики `processedCandles` и `publishedRecommendations` корректно инкрементируются.

---

### Задача 8. Персистентность и идемпотентность (PostgreSQL)
* **Тип:** База данных / Надежность
* **Описание:** Подключить PostgreSQL для сохранения истории свечей, состояния прогонов и дедупликации повторных сообщений по ключу `(runId, instrument, sequenceNumber)`.
* **Ожидаемый результат:** При перезапуске сервис не теряет накопленное состояние и не обрабатывает повторно ранее полученные свечи.
* **Критерии готовности (Definition of Done):**
  - [ ] Подключен Spring Data JPA / PostgreSQL.
  - [ ] Таблицы для фиксации обработанных сообщений и дедупликации.
  - [ ] Повторная свеча с тем же `sequenceNumber` не порождает дублирующей рекомендации.
