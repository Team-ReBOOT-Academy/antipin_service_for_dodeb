## 1. Определение проекта

### Назначение сервиса

Сервис представляет собой автономное серверное приложение, реализующее алгоритмическую обработку рыночных данных. Сервис интегрируется с учебной платформой преподавателя (Teacher Trading Platform) через шину сообщений Apache Kafka, в реальном времени анализирует поток закрытых свечей по финансовым инструментам и формирует торговые рекомендации (BUY, SELL, HOLD).

### Решаемая проблема

Исключение человеческого фактора и субъективных эмоций при принятии решений о сделках, обеспечение детерминированной обработки рыночных данных с низкой задержкой и соблюдение строгого контракта платформы.

### Цели и задачи

- **Цель:** разработать отказоустойчивый, масштабируемый микросервис торговой стратегии, стабильно работающий в распределенной событийной среде.

- **Основные задачи:**

  1. Реализовать надежное подключение к защищенной Kafka (SASL\_SSL SCRAM-SHA-512) с сохранением позиции чтения (offset).

  2. Обеспечить корректный жизненный цикл сервиса (регистрация при старте, периодический heartbeat раз в 5 секунд, graceful shutdown).

  3. Реализовать потоковую обработку закрытых свечей с гарантией дедупликации и идемпотентности.

  4. Обеспечить изоляцию состояния по прогонам данных (`runId`) и инструментам (`instrument`).

  5. Предоставить эндпоинт `GET /health` для контроля состояния компонентов.

### Ожидаемый результат

Автономный контейнеризированный сервис, который при запуске регистрируется на платформе, непрерывно подтверждает свою доступность, своевременно отвечает на каждую закрытую свечу валидной рекомендацией и сохраняет историю в базу данных.

## 3. Взаимодействие с внешними системами

Сервис взаимодействует исключительно с брокером сообщений Apache Kafka преподавательской платформы и собственной СУБД PostgreSQL.

### Используемые Kafka-топики и события

| Топик | Направление | Тип события (`eventType`) | Описание |
| - | - | :-: | - |
| `account.registration.request` | Исходящее | `account.registration.request` | Первичная регистрация сервиса при запуске. Передает `secretKey`, `accountId`, `serviceName`, `strategyId`. |
| `account.registration.result` | Входящее | `account.registration.result` | Ответ платформы о статусе регистрации (`REGISTERED` или `REJECTED`). |
| `account.service.heartbeat` | Исходящее | `account.service.heartbeat` | Периодический сигнал доступности (каждые 5 сек) со счетчиками обработанных свечей. |
| `${CANDLE_TOPIC}` | Входящее | `market.candle.closed` | Поток закрытых свечей с ценами (open, high, low, close, volume) и номером `sequenceNumber`. |
| `strategy.recommendation.created` | Исходящее | `strategy.recommendation.created` | Торговая рекомендация в ответ на свечу с сохранением `sourceEventId`, `runId`, `sequenceNumber`. |
| `strategy.recommendation.result` | Входящее | `strategy.recommendation.result` | Результат обработки рекомендации платформой и обновленное состояние портфеля. |


### Протоколы и безопасность

- **Протокол сообщений:** JSON over Apache Kafka.

- **Аутентификация в брокере:** `security.protocol = SASL_SSL`, `sasl.mechanism = SCRAM-SHA-512`.

- **Авторизация бизнес-событий:** через поле `secretKey` в payload каждого исходящего сообщения (ключ не логируется и не коммитится в Git).

- **Ограничения по времени:** сервис должен отвечать на свечу в пределах окна ожидания прогона (до публикации следующей свечи).


## 4. Состав решения на уровне компонентов

Архитектура сервиса строится по принципу чистой слоистой архитектуры:

1. **HTTP Controller Layer (`HealthController`):** отвечает за мониторинг доступности (`GET /health`), не требует авторизации, отдает текущее состояние подсистем.

2. **Kafka Messaging Layer (Consumers / Producers):** обеспечивает надежный прием свечей и отправку рекомендаций и heartbeat через Spring Kafka. Настроен отдельный уникальный `group.id`.

3. **State & Deduplication Manager:** отслеживает пару `(runId, instrument, sequenceNumber)` и `eventId` для исключения повторной обработки дубликатов сообщений (идемпотентность).

4. **Strategy Engine:** изолированный вычислительный модуль, накапливающий свечи и рассчитывающий индикаторы для генерации сигналов.

5. **Persistence Layer (Spring Data / PostgreSQL):** хранение истории прогонов, фиксация контрольных точек (offsets) и полученных результатов портфеля.

## 7. Допущения и открытые вопросы

1. **Сетевые задержки:** предполагается, что задержка сетевого канала до брокера Kafka не превышает 500 мс, что оставляет достаточный запас внутри окна ожидания свечи.

2. **Параметры подключения:** все чувствительные параметры (`KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_USERNAME`, `KAFKA_PASSWORD`, `SECRET_KEY`) передаются исключительно через переменные окружения и никогда не коммитятся в Git.

3. **Холодный старт:** при первом запуске нового инструмента сервис корректно возвращает сигнал `HOLD` до накопления достаточного окна данных.
